# Decisions and constraints

| Decision | Status | Rationale / alternatives |
|---|---|---|
| Preserve initial dirty worktree; isolate hardening branch | Required / completed | Phase 0 recorded the original checkout state and created `codex/production-hardening-v1` in a separate worktree. Do not modify the original checkout. |
| No production deployment, migration, secret changes, or customer payment | Required | No production mutation was authorized or performed. |
| Phase 0 E2E failures | Classified; retain as baseline | PayPal SDK display failures are subscription-widget/environment failures because `NEXT_PUBLIC_PAYPAL_CLIENT_ID` is absent, not invoice capture/state failures. The mobile plan-header and navigation failures are unrelated. Do not fix them in Phase 1. |
| Invoice signing key | Implemented, release configuration required | New links use versioned `v2.` HMAC with `INVOICE_LINK_SECRET` (minimum 32 UTF-8 bytes). Optional `INVOICE_LINK_SECRET_PREVIOUS` verifies rotated and legacy links. No PayPal-secret fallback. Before release, preserve the actual old signing key as previous if it was previously used; never record its value in docs. |
| Transactional invoice/payment ledger | D1 recommended; implementation/release blocked | `REVIEWS` KV has no transactional compare-and-set across invoice state and payment events. Recommend D1 invoice records, unique PayPal order association, capture/event ledger, and atomic conditional state transitions with uniqueness constraints. No D1 binding/database is configured. Do not provision or migrate production without approval; do not claim KV atomicity. |
| D1 migration/import and rollback | Pending owner approval | Proposed additive schema: invoice table keyed by invoice UUID with integer USD minor units and status; unique nullable PayPal order ID; payment-event table with unique provider/capture/event IDs and foreign key. Dry-run export/import KV records, validate counts/checksums, reconcile paid/order state against PayPal, then pause checkout for cutover. Make D1 authoritative for new writes; keep KV read-only during a reversible observation window. Rollback requires pausing checkout and reconciling/replaying every post-cutover PayPal capture before switching reads; never restore an old snapshot over financial events. |
| PayPal webhook verification and deduplication | Blocked | No webhook endpoint, configured webhook ID, or durable idempotency store exists. Proposed: call PayPal's official `POST /v1/notifications/verify-webhook-signature` with transmission headers, configured webhook ID, and original event body; accept only `verification_status: SUCCESS`. Insert the stable event ID and conditionally transition the invoice in one D1 transaction; acknowledge only after durable commit. Do not add KV-only handling and claim durable deduplication. |
| PayPal merchant identity | Required configuration not supplied | Invoice operations now require `PAYPAL_MERCHANT_ID` and compare it with the order purchase-unit payee. Obtain the exact ID from the account owner/vendor console; do not infer it from client ID or invent a value. |
| Commercial policy unchanged | Required | No pricing, package terms, chatbot functionality, preview-email infrastructure, or customer-facing design changes were made. Owner decisions on text-back/second-number charges and Spain EUR pricing remain open. |
